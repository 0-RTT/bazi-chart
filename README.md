# 八字排盘 · Android（v0.11.0）

面向命理从业者的专业排盘工具。Kotlin + Jetpack Compose，**全程离线**（连 `INTERNET` 权限都没申请）。

输入公历或农历生辰 + 性别 + 出生地，输出四柱、十神、藏干、纳音、旬空、胎元命宫身宫、大运、流年。
命盘页只呈现一张四柱表；旺衰、格局、调候、神煞归属、刑冲合害这些二次推论全部放在断语页，不混在盘面上。

本版三个重点：**日期时间改为滚轮选择**、**排盘后自动生成一段可直接交给大模型的 AI 分析指令**、**历史命例一键复用**。

## 三、关键算法口径

### 时间归一（最大的错误来源）

```
钟表时间（东八区）
  → 经度修正：(经度 − 120°) × 4 分钟
  → 均时差：NOAA 近似式，±16 分钟
  → 真太阳时（定日柱、时柱）
```

实测：乌鲁木齐（87.62°E）12:00 → 真太阳时 **09:37**，**午时变巳时**。不处理这一层，盘直接是错的。

夏令时**不做自动推断**——1986–1991 年区间边界易错，宁可让用户在 `SectConfig.dstOffsetMinutes` 显式填写，也不猜。

### 四柱

| 柱 | 分界 |
|----|------|
| 年柱 | **立春时刻**（不是元旦、不是正月初一） |
| 月柱 | **十二「节」**（立春/惊蛰/清明…），不是「气」 |
| 日柱 | 儒略日锚定，经 tyme4kt 换算 |
| 时柱 | 真太阳时 + 五鼠遁；23 时归属由 `ZiHourSect` 控制 |

### 基础表（全部自研，不依赖库）

十神用 **10×10 常量矩阵**查表（五行生克 × 阴阳同异），不写 25 个分支；藏干、纳音、十二长生、刑冲合害、神煞全部表驱动，改口径不动逻辑。

### 旺衰打分

天干各 1.0；地支按位置加权（**月支 3.0 司权、日支 2.0、年时支 1.0**），支内按藏干本气 1.0 / 中气 0.5 / 余气 0.2 折算。

命例实测（丙寅 癸巳 癸酉 壬子）：

| 五行 | 木 | 火 | 土 | 金 | 水 |
|------|----|----|----|----|----|
| 得分 | 1.0 | 4.5 | 0.8 | 3.5 | 4.0 |

帮身（水 4.0 + 金 3.5）占 54.35% → 偏强；月令巳火失令、日支酉金得地、天干得势；取**正财格**（月令本气丙火透干）；调候主用**辛金**。

每一条加分都能在 UI 上逐项列出，不给黑盒分数。

## 五、界面

风格取「纸、墨、朱砂」三色：暖白纸底、墨色正文、朱砂点睛，衬线字做干支，不用渐变与投影。版式参照问真八字这类专业排盘工具的信息组织方式，但配色与字体是自研的。

**录入页**：年月日时分五列滚轮，改为直接滚动选择，不再手打数字。

- 滚轮用定高 `LazyColumn` + 上下对称留白让选中项落在正中，停手后按偏移量算最近项再动画吸附。**刻意没用 foundation 的 snap fling 实验 API**——那套接口在小版本间改过签名，宁可自己吸附也不赌依赖升级。
- 「日」列的天数按当前年月实时计算：公历走 `LocalDate.lengthOfMonth()`，农历走 tyme4kt 的朔望推算（大月 30 / 小月 29）。**农历月长没有规律，固定 30 天一定会让用户选到不存在的日期。**
- 农历年份自动带出「闰 X 月」选项，插在本月之后，与专业工具的习惯一致。
- 滚轮下方实时显示所属时辰与区间（如「巳时 · 09:00–10:59」），勾了真太阳时换算会额外提示。

**出生地**：内置 34 个省级行政区 + 全部地级市，共 381 条（阿里 DataV 行政区划转出，
取地级市中心点）。选择框按省筛选，也可直接输入城市名或省份名。

旁边一个「定位」：只要粗定位权限，取本机经纬度后，城市名取最近的地级市（给人看），
经度用实测值（给真太阳时算）。**不做逆地理编码**——那要联网，而本应用连 INTERNET 权限都没有。

> 为什么不列出全部两千多个县区：列进来搜索反而更难用，而且县城与其所属地级市的经度差
> 通常在 0.5° 以内（2 分钟），对时辰判定无影响。真在意精度，就用「定位」取实测值。

**命盘页**：一张十一行的四柱表占满整屏宽度——日期（表头）、主星、天干、地支、藏干、副星、星运、自坐、空亡、纳音、神煞。行标在左、四列等宽、列间 0.5dp 细线，天干地支用 30sp 衬线大字按五行着色，右下角跟一个 12sp 的五行本字（甲木、午火），日柱主星一格写「元男/元女」标朱砂。表下只有胎元命宫身宫与本命旬空，不再挂其它推论。

> 五行原来画的是树、焰、山、菱、滴五种多边形。五种形状之间没有共同语言：不认字看不懂，认字也得先记住五种图形。v0.8.0 换成「木火土金水」本字——颜色与文字冗余表达同一信息，扫视（看色）与细读（看字）都成立。

**运程页**：三级下钻。横向大运带（可点选，当运标朱砂）→ 选中某步运后铺开它的十个流年格子 → 点任一流年，下方展开该年十二个流月（月建、干支、十神、交节日，当月高亮）。干支在运程页按本字五行分色：把「庚午」整串染成金色是错的读法，庚属金、午属火。

（断语页已于 v0.6.0 下线，见后文说明。）

## 六、盘面文本

排盘一完成，`AiPromptBuilder` 就同步生成一份 Markdown 文本（`ChartBundle.aiPrompt`），
在「AI」页可一键复制，或从命盘页底部的横幅进入。

v0.9.0 起文本分两段：**任务** 与 **数据**。

任务段写死了这些要求——先校盘（不一致先指出再按下表继续）、五种流派交叉验证
（子平格局／旺衰扶抑／调候／盲派取象／神煞旁证）且冲突时不许和稀泥、七个维度逐项
（事业／财运／婚恋／子女／六亲／健康／学业）、关键事件四项（时间范围／吉凶属性／
影响程度四级／具体影响）、结论要注明依据、建议分三档、不确定要说明、最后给输出格式。

数据段仍然只陈述事实：四柱、藏干、副星、纳音、空亡、落空、神煞（按柱列名）、
大运、流年、流月。旺衰、格局、调候、喜用这些**结论**一概不给——那是模型该算的，
先给了它，它就只会顺着抄。

**四节，只收基本信息**：

```
一、排盘    性别、公历、真太阳时、时差校正、农历、出生地、节气、起运、胎元命宫身宫
            四柱表：主星·天干·地支·藏干·副星·纳音·星运·自坐·空亡·落空
二、大运    十步：干支·虚岁·年份·干十神·支十神·星运·纳音·空亡
三、流年    参考年前 5 年至后 15 年，含十神·纳音·空亡·所属大运
四、流月    当年十二个月建：干支·十神·纳音·空亡·交节·终节
```

神煞、旺衰、格局、调候、刑冲合害一概不进文本。理由不是它们不该论，
而是**同一张盘换套查法就能得出不同结论**，写进文本等于把争议当成事实交给模型。
盘面只给能逐格核对的干支，推论留给使用者。

要拿它做什么，由读者自己决定。全文离线生成，`AiPrompt.kt` 里没有一行网络代码。

## 七、v0.3.0：三个修复与历史命例

### 修复一：返回后再点排盘没反应

根因是两层叠加，两层的判据都是**对象相等性**：

1. `MutableStateFlow` 用 `equals` 去重。同一个生辰重排一次，产出的 `ChartBundle` 与上一次逐字段相等，
   `_state.update { it.copy(result = newBundle, loading = false) }` 得到的新值与旧值相等，**状态根本不发射**，
   UI 连重组都不会发生。
2. 即便发射了，`LaunchedEffect(bundle)` 的 key 也是按 `equals` 比较的——key 没变，副作用不会重启。

所以「再点一次排盘」什么都不会发生。而切换历法改变了输入、算出的是另一张盘，才「碰巧」能重排——这正是你观察到的现象。

修复：路由改成 ViewModel 里的显式 `showResult`，配合每次成功排盘自增的 `revision`；Composable 只读状态，
不再用副作用监听命盘对象。顺带的好处是旋转屏幕后仍停在结果页。

### 修复二：选了时间，排出来还是 1990

根因在滚轮取索引的算法。旧实现用定高 `LazyColumn` + `contentPadding` 做居中，
再用 `firstVisibleItemIndex + firstVisibleItemScrollOffset / itemHeight` 反推选中项。这个反推是错的：

- `firstVisibleItemIndex` 指的是**第一个可见项**，而居中项前面永远还压着 `visibleCount / 2` 项
  （它们被画进了 `contentPadding` 区域），于是读出来的索引比视觉中心小 2；
- 这个偏了 2 的索引又被 `scrollToItem` 拿去重新定位，滚一次偏一次，最终表现就是「怎么选都还是原来那个年份」。

修复：滚轮改成自绘。位置是一个连续的 `Float`（单位＝行），第 `i` 行偏移 `= (i - position) * itemHeight + centerTop`，
选中项 `= round(position)`——绘制和取值用的是**同一个量**，不存在两套口径。停手后按速度做一次短程投影再吸附。
另外在滚轮下方直接写出「将被使用的值」（如 `公历 1995-03-08 14:20 · 申时`），排盘用的是不是这一行，一眼可见。

### 新增：历史命例

- 每次排盘成功自动入栈；同一生辰不重复堆积，顶到最前；上限 30 条。
- 存 `SharedPreferences` 自定义行格式，不引 Room、不引序列化库；解析失败的行直接跳过，坏数据不连累排盘。
- 只存「输入 + 四柱/农历两个展示文本」，不存整张命盘——重算一次不到 50ms，存整盘（含 100 年流年）体积要大几十倍，
  还会在引擎口径调整后留下陈旧数据。
- 录入页顶部「最近排盘」：默认 3 条、可展开全部，点一条回填并**立即重排**，单条可删、可一键清空。

### 顶部样式

Material 的 `TopAppBar` 是 64dp 直角矩形 + 直角下沿，和卡片的 16dp 圆角不是一套语言——这就是「顶部直角」的来源。
换成自定义 `ScreenHeader`：56dp、32dp 圆形返回键、衬线标题 + 副标题；页面内切换从下划线 Tab 换成与「公历/农历」
同款的胶囊 `Segmented`；面板圆角统一 16dp、分段块 12dp、标签 5dp。

### v0.3.1 补修：头顶那条直角

v0.3.0 换掉了 `TopAppBar`，但真机上头顶仍是直角。原因不在 Compose，在**系统窗口层**：

- `AndroidManifest.xml` 直接挂着平台主题 `@android:style/Theme.Material.Light.NoActionBar`，
  项目里没有 `res/values/themes.xml`；
- `MainActivity` 没有调用 `enableEdgeToEdge()`，窗口还在「decor 独占系统栏」的老模式里。

于是状态栏由系统按自己的规则画一层深色底，内容从状态栏下沿才开始，两块拼起来的接缝是一条
贯穿屏宽的直角硬边——和头部用什么组件完全无关，改多少次 `ScreenHeader` 都不会消失。

修法是三件事：

1. 新增 `res/values/themes.xml` 与 `values-night/themes.xml`，`windowBackground` 对齐

### 移除的四块

五行力量、格局与调候、神煞清单、刑冲合害，四个面板全部从命盘页撤掉。

### 为此新增的两项数据

表里有两行原引擎没有，不是排版问题，是数据不够：

**自坐** 与 **星运** 不是一回事。星运是日主落在各支的十二长生，
自坐是本柱天干坐本柱地支的十二长生。日柱两者必然相同（本就是日主坐日支），
其余三柱通常不同。以构造盘「丁酉 甲申 丙午 壬寅」为例：

| | 年柱 丁酉 | 月柱 甲申 | 日柱 丙午 | 时柱 壬寅 |
| --- | --- | --- | --- | --- |
| 星运（日主丙） | 死 | 病 | 帝旺 | 长生 |
| 自坐（本柱干） | 长生 | 绝 | 帝旺 | 病 |

**空亡** 也一直被理解窄了。原模型只有一个 `isEmptyBranch`（该支是否落日柱旬空），
但表里的「空亡」是**每柱自身干支所属之旬的两个空支**，四柱各不相同。
六十甲子分六旬，每旬十干配十二支，多出的两支即空亡：
己卯、甲戌同属甲戌旬，空申酉；丙午属甲辰旬，空寅卯；壬辰属甲申旬，空午未。

两者语义不同，不能合并，所以 `Pillar` 现在同时保留：

- `voidBranches` —— 本柱旬空两支，表格「空亡」行用它；
- `isEmptyBranch` —— 该支是否落日柱旬空，AI 文本另立「落空」一行用它。

AI 文本的四柱表也同步补上「自坐」与逐柱「空亡」，并新增「落空」一行。

## 十一、v0.7.0：时柱默认不校正、神煞按多盘重查

### 一、时柱错一个时辰：默认值的问题，不是算法的问题

用户反馈：同一时间在通行工具里是辰时，本应用却排出卯时——差一个时辰。
四柱前三柱一致，只有时柱不同。

先确认算法本身有没有错：以东经 116.4° 为例，经度差 `(116.4 − 120) × 4 = −14.4` 分，
冬季均时差约 `−6` 分，合计约 `−20` 分，与界面显示的校正量吻合。
07:00 减 20 分是 06:40，确实落在卯时（05:00–06:59）。**计算是对的。**

错在**默认开启**。真太阳时是把钟表时换算成日晷时，它在天文上更"真"，
但通行排盘工具默认按钟表时定时辰，两者在贴着时辰边界出生时会差一个时辰——
07:00 正好踩在辰时起点，减 20 分就退回卯时。

改法：`SectConfig.useTrueSolarTime` 默认 `false`，与通行口径一致；
需要校正的用户在录入页显式开启，开关说明里写明「贴着时辰边界出生时，开启会改变时柱」，
录入页的时辰提示也改为「按钟表时定时辰 / 已开真太阳时，时辰可能变动」。

回归测试钉死这一条：默认配置下 07:00 生于东经 116.4° 取辰时，显式开启后落到卯时。
两个断言同时存在，任何人把默认值改回 `true` 都会立刻失败。

顺带修了一处显示：农历原先只写干支年，与公历年差一岁时会让人以为排错年。
改为「公历年 + 月日 +（干支年）」，形如 `1990年正月十五（庚午）`。

用户对照后指出「神煞又对不上」。逐柱点数，差异不是几条而是整批：

| --- | --- | --- | --- | --- |
| 修正前 | 0 项 | 3 项 | 4 项 | 1 项 |
| 修正后 | 2 项 | 9 项 | 8 项 | 4 项 |

#### 四处「必须收窄」，兼看反而错

这几条是这次排查中最花时间的——通行口诀只写"某干见某支"，
不写"从哪个字查"，而一查错就会凭空多出神煞：

- **红艳煞只看日干**。若并查年干，年干所见之支一旦落在时柱，时柱就会多一项——
  而通行工具并不列，故收窄为单查日干。
- **天喜只以年支查**。兼看日支的话，年支所主的那一格会在年柱重复出现一次。
- **阴差阳错只查日柱**。时柱干支也可能落在那十二组里，兼看就会多一项。
- **丧门只列，不列吊客**。两者成对出现，但对照结果只列丧门，不自作主张补。

反过来，**天乙、国印、金舆、福星必须并查年干与日干**：
同一张盘里，往往有一柱的贵人之支只能由年干推得、另一柱只能由日干推得。
单看任何一个干，都会漏掉另一半，而漏掉的往往是年柱或时柱——最显眼的位置。

#### 两个真正的 bug

**华盖自指**：日支未属亥卯未，华盖正是未——若不排除"以日支查日支"，
日柱会凭空多出一个华盖。实测没有。修法是把 `Rule.match` 的第一个参数改为宫位，
华盖规则写成 `z == canopy && pos != basePos`；运柱传 `null`，不参与排除。

**童子煞只算了纳音法**：上一版结论是「按年纳音取」，因为秋月生的盘
只有纳音法能解释时柱上的那一项。但换一张盘后，日柱与时柱同时出现童子煞，
其中日柱那一支在纳音法里取不到，只能用季节法（冬夏见卯未辰）。
两法并用才对：`纳音法 ∪ 季节法`。

#### 为什么这次能查准：多张盘一起用

单张盘只能证明"查得到"，不能证明"不乱查"。上面每一条"并查还是单查"的取舍，
在一张盘里两种口径往往同时成立，换一张盘才分得清。
所以校验脚本 `verify_shensha.py` 用**三张构造盘、31 个柱·神煞组合**做集合精确比较——
多一项、少一项、位置错都失败：

```
构造盘一 丁酉 甲申 丙午 壬寅：4 + 5 + 8 + 8 = 25 项
构造盘二 乙巳 丁卯 庚申 壬辰：4 + 2 + 7 + 5 = 18 项
构造盘三 丁巳 戊申 丙辰 癸未：4 + 7 + 4 + 4 = 19 项
```

上一版只比「有没有」，于是漏九项、多一项也照样通过。集合相等才是真对撞。

**隐私说明**：这三张盘是为覆盖查法而构造的合法干支组合，不是任何真实命例。
定位口径时曾用外部实测结果校对，那些命例连同出生时间、地点一律不入库，
测试、脚本、文档里都不出现。

## 十三、v0.9.0：AI 指令重写、城市库补全与定位

### 一、AI 文本从「只给数据」改成「任务 + 数据」

早先的设计是只给盘面、不给指令，理由是「读者要拿它做什么，由读者自己决定」。
实际用下来这条站不住：每次都要重打一遍分析维度与输出要求，十次有八次会漏掉
「关键事件要给时间范围」。要求写死在生成端，盘与问才不走散。

新增任务段八节：先校盘、多派交叉、七个维度、关键事件四项、结论要能核对、

- **冲突不许和稀泥**：各派结论不一致时，必须写明分歧点、采信哪一派、依据是什么。
  「综合来看」这种把冲突抹平的写法，等于没分析。
- **时间范围不许含糊**：要落在表里的大运与流年上，不许出现「二十几岁」「中年」。

数据段同步补了神煞一行（按柱列名，空亡不重复列）。神煞由 app 层转成字符串传进来，
`core:interpret` 依然不依赖 `core:analysis`——依赖边界没破。

- 选择框加省份筛选条（34 个省，横向可滑），输入框同时匹配城市名与省份名

## 十四、v0.10.0：运程页等高、动效口径统一

### 一、当运那一格比邻格高一行

大运带的十格本该等宽等高，实际渲染出来，标着「当运」的那一格比左右邻格往下多出
一行，整条带子的下沿成了锯齿。原因只在一行代码：

```kotlin
if (current) {
    Spacer(Modifier.height(2.dp))
    Text("当运", fontSize = 9.sp, color = primary)
}
```

这一行字只在当运时渲染，于是那一格的内容比邻格多一行——`Column` 的高度由内容决定，
`LazyRow` 又不会把各格拉到同高，差值就直接显示出来了。

修法不是把「当运」删掉（那是唯一能区分「当运」与「已选」的标记），而是给它一个固定
13dp 高的槽位（`CHIP_FOOT`），**无论是否当运都占位**，只在当运时写字。

没有直接给整格写死一个总高度：那样系统字号放大时会溢出。让结构恒定，高度自然一致。

### 二、动效散落各处、各写一套

原来只有 Compose 的默认 spring 和无动画两种状态：选中是一帧之间翻色，换大运是整块
文字直接换掉，页签切换是整屏替换。单看每一处都不算错，叠在一起就是「不顺」。

新增 `Motion` 三档口径，全站只此一处定义时长与缓动：

| 档 | 时长 | 用在哪 |
|---|---|---|
| `state` | 220ms | 选中底色、边框色、边框粗细（0.5 ↔ 1dp）、字色 |
| `swap` | 180ms | 换大运、换流年、换流月（只做交叉淡入） |
| `page` | 200ms | 页签切换、进出命盘 |

统一 `FastOutSlowInEasing`：起步快，按下的一瞬间就有回应；收尾慢，停下来的位置看得清。
线性或 EaseIn 在触屏上都会显得「黏」。

落地的地方：

- **大运带选中后自动居中**。原来点到第 7 格时它可能已经在屏幕外，点了却看不见点了哪个。
  居中前用 `snapshotFlow` 等首次布局产出可见项——首帧的 `scrollToItem` 会被静默丢弃，
  不等就白滚。
- **三级下钻全部交叉淡入**。动画期间 content 每帧重组，所以流月与流年的筛选结果都过
  `remember`，否则 180ms 里要重算十二次节气。
- **分段选择器**（页签、性别）选中块与字色过渡，不再一帧翻白。
- **进出命盘**交叉淡入：录入页与命盘页是两种完全不同的版式（表单 vs 表格），
  硬切会让人分不清「排盘成功了」还是「页面闪了一下」。

### 三、点大运，流月不动

这是这一版修掉的一个功能性 bug，不是观感问题。

三级下钻的口径是 **大运 → 流年 → 流月**，其中流月跟的是「选中的那一年」。但点击大运
只改了「选中哪一步运」，没改「选中哪一年」——于是换运之后，流月仍然停在上一运的年份上。
如果用户从未点过流年，那一年更是恒等于今年，点任何大运流月都不动。

现在点大运时一并把选中年份挪进这步运：含今年就用今年（点「当运」那格不跳走），
否则落到这步运的第一年。重复点同一格不再重置，免得把刚选好的流年冲回运首。

### 四、依赖

`androidx.compose.animation:animation` 改为显式声明。`material3` 只带 `animation-core`，
而 `Crossfade`、`animateColorAsState`、`animateDpAsState` 都在完整包里——此前是靠
`foundation` 的传递依赖偶然可用，不算数。

### 五、校验

新增 `tools/verify/verify_motion.py`（53 项，已进 CI），只查两件「看不出来的事」：

- **结构是否保证等高**：底注槽存在、宽度只来自一个常量、禁止 `if` 决定是否渲染「当运」
- **动效是否只有一套口径**：三档时长、禁止在 UI 文件里硬编码 `tween`、五处交叉淡入点、
  六处过渡、三级下钻的联动逻辑

九脚本合计 **1069 项断言**（原 1020）。

## 十五、v0.11.0：页签移到底部、切换改用 Pager、流月补节名

### 一、页签从顶部移到底部

三个页签是「同一份数据的三种看法」，属于平级切换，不是「往上一层」。放在屏幕下方
是拇指的自然落点，比放在标题下方少一次伸手；顶部那 56dp 只留盘名与返回。

底部栏自己承担手势导航条的 inset（`navigationBarsPadding`），内容区因此在它上方
自动收边，不会被挡住。选中态用两道冗余编码：字色 + 上方一道短杠——只靠字色，
强光下或色觉有差异时会糊。短杠的透明度与横向缩放走 `graphicsLayer`，只改绘制层，
不触发重排。

### 二、切换动画：从「交叉淡入」改成「并排 Pager」

上一版给页签加了 200ms 交叉淡入。**效果比不加更怪**，原因很具体：命盘、运程、
AI 三页都是整屏长列表，淡入淡出期间两张内容同时存在、位置又不同，同一帧里能看到
两份错位的文字，读起来像重影。

改成 `HorizontalPager`：三页等宽并排，切换是真正的横向位移，由手指直接驱动——
可以拖到一半反悔，松手自己落到最近一页。位移只在水平和垂直各自的滚动轴上发生，
不会和列表自身的纵向惯性打架。

针对高刷屏的两处处理：

- `beyondViewportPageCount = 1` 预组合左右各一页。否则第一次向左滑时，目标页要等
  手指已经动了才开始组合与测量，第一帧就掉帧。三页都不重，多备一页的代价远小于掉帧。
- 点击页签走 `animateScrollToPage` + `tween(260)`，不用默认 spring：spring 在跨两页时
  容易过冲，260ms 的缓出更稳。

顶部路由（录入页 ↔ 命盘页）也从交叉淡入改成 **淡入 + 屏宽 1/14 的横向位移**。
这两页是两种完全不同的版式（表单 vs 表格），纯淡入同样会叠成重影；加一点同向位移，
眼睛读到的是「翻过去了一页」。

### 三、流月：日期看起来「固定」，是因为只显示了月日

有人问「不同年份的流月是不是固定的？月份会变，但下面的新历日期一直没变」。

数据没停，是显示精度不够。十二节的交节时刻每年后移 5 小时 49 分，遇闰年再前移一天；
净效果是——**时刻每年都不同，月日多数只差 0–1 天**。而大运是十年一步，
连着点两三步，那一格常常还是「2/4」。

现在流月格改成显示 **节名 + 交节日**（`立春 2/4`），节名让「哪一天交哪个节」读得出来。
`MonthlyFortune` 补了 `jieName` 字段，与 `startTime` 同源。新增 `SolarTermsTest`
把这件事钉住：连续四年的立春时刻必须互不相同、相隔十年也必须不同，同时断言月日
**允许**相同——「看起来没变」是精度问题，不是数据停了。

```bash
# 本地编译需要：JDK 17+、Android Studio（含 SDK Platform 34）

```

技术栈：Kotlin 2.0.21 / AGP 8.6.1 / Compose BOM 2024.09.03 / tyme4kt 1.5.2（MIT）/ minSdk 26 / targetSdk 34。

> minSdk 取 26 是因为核心引擎用 `java.time`，26 起原生支持，省掉 desugaring 依赖。若要下探到 24，需开启 `coreLibraryDesugaring`。

### 云端构建（GitHub Actions）

`.github/workflows/android.yml` 已配好，推到 GitHub 后自动执行：

1. `verify-engine` —— 跑八个 Python 校验脚本（906 项断言）。算法不对，后面直接不构建。
2. `build` —— 装 JDK 17 + SDK 34，跑 `:core:calendar:test` / `:core:bazi:test` / `:core:interpret:test`，再构建 Debug APK。
3. 产物 `bazi-debug-apk` 挂在 Actions 页面该次运行的 Artifacts 中，下载即可安装。

这样即便本机没有 Android 环境，也能拿到可安装的 APK。构建失败时 `build-reports` 会带上 Gradle 报错与测试报告。

## 十七、已知限制与待办

**未实现（P1/P2）**

- 命例本地存储（Room）、命例对比
- 导出 PNG / PDF、分享
- 时辰未知时的三柱容错模式
- 城市库到地级市，未覆盖区县；暂无手动输入经纬度。定位可绕开这一层
- 定位只申请粗定位：室内可能只拿到基站/ Wi-Fi 级别的点，经度误差 0.05° 量级（十几秒），
  对时辰判定无碍；若系统定位关闭或机型为 Android 10 及以下且无历史位置，会明确提示手选
- 格局仅月令取格主路径，未做从格、专旺格、化气格（且不上屏，见第二节）
- 神煞 38 种，血刃、披麻、天罗地网、六厄、灾煞**有意不收**——查法在几种「神煞大全」
  之间互相矛盾，落不到统一口诀；宁可少一项，不可多一项错的。详见 `docs/规则审查-v0.8.md`

- APK 由 CI 的 debug 签名产出，**每次构建签名不同**，覆盖安装前须先卸载旧版，
  本地命例随之清空。要长期当日常工具用，应改为固定密钥的 release 签名
  （需要在仓库放一份 keystore，或配 CI secret——两者都要先定下仓库是否转私有）

**数据待专业审校**

- **调候表**：依《穷通宝鉴》通行本录入 10 干 × 12 月令，主用较确定，**辅助用神各版本取舍有出入**，建议从业者核对后再上线。
