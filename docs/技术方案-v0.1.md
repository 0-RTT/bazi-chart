### 1.2 关键结论：不要从零写历法，但要自己写八字语义层

调研下来最重要的一条判断——把所有计算拆成**两类**，架构完全不同：

| 层 | 特征 | 例子 | 策略 |
|----|------|------|------|
| **唯一答案层** | 有客观正确的唯一结果，可由天文算法验证 | 节气时刻、朔望、公农历转换、日柱干支、儒略日 | **直接用 tyme4kt**，别重造。错了就是错了，没有流派可辩 |
| **流派分歧层** | 各家典籍口径不同，没有唯一正确答案 | 神煞查法、早晚子时、格局取法、旺衰权重、调候用神 | **必须自研 + 做成可配置策略**，用别人库反而被绑死 |

这个分层是整个技术方案的骨架：**底座买现成，语义自己掌**。

### 1.3 具体可借鉴之处

1. **tyme4kt 的 `EightCharProvider` 策略接口** —— 它把"23:00–23:59 算今天还是明天"抽象成可替换 Provider（`DefaultEightCharProvider` / `LunarSect2EightCharProvider` / 自定义）。这就是我们做**流派开关**的标准范式，直接照此设计 `SectConfig`。
2. **lunar 的 `eightchar` 包分层** —— `EightChar` → `ChildLimit`（童限/起运）→ `DecadeFortune`（大运）→ `Fortune`（小运）。这个对象图谱比"一个大函数返回一个 Map"清晰得多，值得复用其命名与关系。
3. **bazi-skill 的知识库形态** —— 把典籍规则拆成 `wuxing-tables.md` / `shichen-table.md` / `dayun-rules.md` / `classical-texts.md` 四类纯数据文件。我们落成 **JSON 资源**（`rules/tiaohou.json`、`rules/geju.json`、`rules/shensha.json`），规则与代码彻底解耦，改口径不用发版重新编译逻辑。
4. **baziziwei 的 analyzer 三段式** —— 结构化中间量 → 规则匹配 → 文案拼装。这是我们解读引擎的骨架，避免写成一堆 `if` 嵌套。
5. **china-testing 的五行打分** —— 它把旺衰量化成可展示的分数条。对专业用户很有说服力，但要**保证可解释**（每个加减分项都要能列出依据），不能黑盒。

## 三、核心排盘算法实现思路

### 3.1 第一步：把时间归一（最容易错的地方）

绝大多数排盘软件的 bug 出在这一步，而不是四柱公式。

```
钟表时间（用户输入，默认 UTC+8 北京时间）
   ↓ ① 夏令时修正：1986–1991 年中国实行夏令时，若落在区间内需 -1 小时
   ↓ ② 时区历史：1929 年前中国采用北京地方平时，时区基准与今日不同
   ↓ ③ 经度修正：地方平太阳时 = 钟表时间 + (出生地经度 − 120°) × 4 分钟
   ↓ ④ 均时差修正：真太阳时 = 地方平太阳时 + EoT(年内日序)
真太阳时 → 定日柱、定时柱
```

- **经度修正**是最容易被忽略的：乌鲁木齐（87.6°E）与北京时间差 **约 130 分钟**，足以跨两个时辰。
- **均时差** EoT 在 ±16 分钟内波动，用天文近似公式（约 10 项谐波）即可，精度足够。
- **产品决策**：真太阳时开关默认**开**，且界面上同时展示"钟表时 / 真太阳时"两行，让用户知道差在哪。这既专业，也避免了"凭什么给我换时辰"的争议。

### 3.2 四柱

| 柱 | 分界依据 | 算法 |
|----|----------|------|
| 年柱 | **立春时刻**（不是元旦，不是正月初一） | 以立春为界取干支年，干支序号 = (干支年 − 4) mod 60 |
| 月柱 | **十二「节」**（立春/惊蛰/清明/立夏/芒种/小暑/立秋/白露/寒露/立冬/大雪/小寒），**不是「气」** | 由节气定月支，月干用五虎遁：甲己之年丙作首、乙庚之岁戊为头、丙辛必定寻庚起、丁壬壬位顺行流、戊癸之年甲寅求 |
| 日柱 | 连续 60 日循环，与节气无关 | 儒略日 JDN 锚定基准日 → `干支序号 = (JDN + offset) mod 60`，offset 由已知基准日反推并用万年历回归校验 |
| 时柱 | 每 2 小时一辰，子时 23:00–01:00 | 时支由真太阳时定，时干用五鼠遁：甲己还加甲、乙庚丙作初、丙辛从戊起、丁壬庚子居、戊癸壬子 |

⚠️ **「节」与「气」的区别是新手第一大坑**：立春、惊蛰是「节」（换月），雨水、春分是「气」（不换月）。24 节气里只有 12 个「节」决定月柱。

⚠️ **早晚子时**：23:00–23:59 出生，日柱算当天还是次日，两派都有。tyme 已经抽象成 `EightCharProvider`，我们做成设置项 `ZiHourSect.EARLY / LATE`，并在命盘上标注当前采用哪一派。

### 3.3 十神：查表，不要写分支

以日干为「我」，对目标天干按 **五行关系 × 阴阳同异** 二维查表：

| 五行关系 | 同性 | 异性 |
|----------|------|------|
| 同我（比劫） | 比肩 | 劫财 |
| 我生（食伤） | 食神 | 伤官 |
| 我克（财） | 偏财 | 正财 |
| 克我（官杀） | 七杀 | 正官 |
| 生我（印） | 偏印 | 正印 |

实现上建一个 `10×10` 的 `Array<TenGod>` 常量表，O(1) 查表。用 `when` 写 25 个分支是最常见的劣化写法，难维护且易漏。

```kotlin
// 十神查表：行=日干(0..9)，列=目标干(0..9)
object TenGodTable {
    private val matrix: Array<Array<TenGod>> = buildMatrix()
    fun of(dayStem: Int, targetStem: Int): TenGod = matrix[dayStem][targetStem]
}
```

### 3.4 藏干 / 纳音 / 旬空

- **藏干**：12 地支 → 本气/中气/余气 固定表（如 寅 → 甲丙戊）。纯查表，注意"余气"各家略有出入，落成配置。
- **纳音**：60 甲子 → 30 个纳音名，两两一组（如 甲子乙丑 → 海中金）。查表最简单；也可用大衍之数推算，但没必要。
- **旬空**：由日柱所在旬推出，`旬空 = 该旬缺失的两个地支`。

### 3.5 大运：顺逆 + 起运折算

**方向**：阳年男 / 阴年女 → **顺排**；阴年男 / 阳年女 → **逆排**（以年干阴阳定，不是年支）。

**起运**：
- 顺排：从出生时刻数到**下一个「节」**的时长
- 逆排：从出生时刻数到**上一个「节」**的时长

**折算率**（核心比例，别记错）：

```
3 天 = 1 年    →   1 天 = 4 个月   →   1 个时辰(2h) = 10 天   →   1 分钟 ≈ 2 小时
```

精确实现用分钟级折算，避免"3 天整"的粗粒度误差：

```kotlin
// minutesToJie: 出生时刻到目标节的分钟差
val yearsExact = minutesToJie / (3.0 * 24 * 60) * 1.0      // 年
// 再拆成 X年Y月Z天 展示，并用 BirthInstant + yearsExact 推出交运具体年月日
```

**大运干支**：从月柱起，顺排则 +1 递进，逆排则 −1 递进，每运 10 年。同时给出 `起运虚岁` 与 `交运公历年月`，两者都要显示——从业者两种口径都用。

### 3.6 流年 / 小运

- 流年干支以**立春**为界的年干支；给出 1–100 岁逐年表。
- 流年与大运、命局构成三方作用：先算「大运 vs 命局」，再算「流年 vs (大运+命局)」，**顺序不能反**，这是断事的基本层次。

### 3.7 神煞：表驱动的规则 DSL

神煞数量多（常用 30+）、查法各异，必须表驱动，不能硬编码。建议数据结构：

```json
{
  "id": "tianyi-guiren",
  "name": "天乙贵人",
  "basis": ["DAY_STEM", "YEAR_STEM"],
  "lookup": { "甲": ["丑","未"], "戊": ["丑","未"], "乙": ["子","申"] },
  "targets": ["YEAR", "MONTH", "DAY", "HOUR"]
}
```

这样加一个神煞 = 加一条 JSON，不改代码；不同流派 = 不同 JSON 文件。常用集合：天乙贵人、文昌、桃花（咸池）、驿马、华盖、将星、羊刃、禄神、空亡、天德/月德、孤辰寡宿、红鸾天喜。

### 3.8 旺衰 / 格局 / 调候（进阶三件套）

**旺衰**——加权打分，但必须**可解释**：

```
总分 = 月令得分（权重最高，司权）
     + 通根得分（地支藏干中有无同类五行，本气/中气/余气权重递减）
     + 透干得分（天干有无同类五行帮扶）
     + 生扶得分（印星生我）
     − 克泄耗（官杀克、食伤泄、财耗）
```

UI 上把每一项加减分**逐条列出**（"月令寅木司令 +30"、"日支坐午火失地 −10"），这比只给一个"身弱"结论有说服力得多，也是区别于免费 App 的地方。

**格局**——以月令为纲：月令本气或中气透干 → 定格（正官格/七杀格/正财格/偏财格/食神格/伤官格/正印格/偏印格）；月令为比劫 → 建禄格 / 月劫格 / 羊刃格。取格优先序（透干 > 本气 > 中气）要做成显式规则，因为各家分歧就在这个优先级上。

**调候**——《穷通宝鉴》口径，本质是一张 **10 日干 × 12 月令** 的用神表（如 甲木生寅月 → 丙火为主、癸水为辅）。直接落成 JSON 表，调候是最适合"查表"的一类知识。

### 3.9 校验策略（专业工具的护城河）

排盘软件的口碑全在"准不准"，必须建立机器可验证的校验体系：

| 手段 | 做法 |
|------|------|
| **黄金样本回归** | 用《中国天文年历》+ 2–3 款权威排盘工具生成 fixture，覆盖 1900–2100 关键日期，断言 ≥ 3000 条 |
| **三源交叉验证** | tyme4kt / lunar-java / sxwnl 三者的节气时刻互相对齐，取最大偏差 < 1 分钟为通过 |
| **边界用例专项** | 立春前后 1 分钟、每个节气时刻前后 1 分钟、23:00 / 23:59 / 00:00、闰月、1986–1991 夏令时年份、1929 年前、农历腊月三十 vs 廿九 |
| **属性测试** | 任意 60 天间隔的日柱必不重复；任一年 12 个「节」时刻严格递增；干支循环周期恒为 60 |

```kotlin
data class BaziChart(
    val pillars: List<Pillar>,           // 年月日时，含干/支/十神/藏干/纳音/长生
    val meta: ChartMeta,                 // 胎元、命宫、身宫、旬空、真太阳时校正量
    val luck: LuckCycle,                 // 起运岁数、交运时刻、大运列表
    val annuals: List<AnnualFortune>,    // 流年
    val analysis: AnalysisResult?        // 旺衰/格局/调候/神煞/刑冲合害
)
```

这个契约一旦锁定，UI 层只渲染、不计算，引擎只计算、不管展示——两边可以并行开发，前端甚至能先用 mock 数据做界面。

### 4.3 性能预算

| 操作 | 目标 | 手段 |
|------|------|------|
| 单次排盘（含 100 年流年） | < 50 ms | 全部在 `Dispatchers.Default`，节气表按年懒加载并缓存 |
| 应用冷启动 | < 1.2 s | 城市库按需加载，首屏只读设置 |
| 命盘滚动 | 60 fps | Compose 稳定键 + `derivedStateOf`，避免重组抖动 |

### 4.4 风险与开放决策

| 风险 | 说明 | 应对 |
|------|------|------|
| **内容合规** | 应用商店对"算命/占卜"类目有限制，国内上架可能被拒 | 定位为「传统历法 / 文化研究工具」，命名与商店描述避开"算命"，加显著免责声明；优先 Google Play |
| **流派分歧引发差评** | 专业用户对口径极敏感，一个神煞查法不同就给差评 | 每个分歧点做成设置项 + 命盘上标注本次采用的口径，把"分歧"变成"专业感" |
| **规则库工作量** | 神煞+格局+调候全套，规则条目约 300–500 条、解读文案 1000+ 条 | 这是本项目最大工作量项，建议规则库独立版本化（JSON 资源包），可热更新 |
| **tyme4kt API 变更** | 上游 v1.5.2 仍在迭代（近期有 `getMonthWithLeap()` 废弃等破坏性改动） | 锁定版本；`:core:calendar` 做一层防腐适配器，上游升级只改一个文件 |
| **精度责任边界** | 1900 年前 / 2100 年后数据可靠性下降 | 明确支持区间（建议 1900–2100），超出范围给提示而非静默出错 |

## 六、待你决策的开放项

1. **支持时间区间**：建议 1900–2100。若要覆盖民国及更早（从业者可能查老命例），需额外处理 1929 年前时区基准，工作量 +15%。
2. **城市经纬度精度**：按地级市（约 340 条）够用，按区县（约 2900 条）更专业但包体 +400KB。建议地级市 + 支持手动输入经纬度。
3. **时辰未知**：是否提供"只排三柱"模式。真实场景很常见（老命例），但会让命盘布局多一套分支。
4. **规则库首发范围**：全套 300–500 条规则一次做完，还是先做高频 100 条（神煞 30 + 格局 10 + 调候 120）？
